# RAMENG usability corrections — 13 November 2026

## Changes

- Outgoing Hebrew email has explicit RTL direction and right alignment on each unformatted text block in the actual MIME HTML. The body occupies the full message width: live Gmail inspection revealed the old 640px wrapper left blank space on the right, even when its paragraphs were correctly aligned. Explicit alignment chosen in the editor remains intact. Plain-text API messages also receive an escaped HTML alternative. Sanitization, bounded inline images and attachments remain supported.
- Inbox threads can be replied to without opening or assigning a project. Replies retain the Gmail thread and RFC reply headers, use the most recent incoming sender, retain account-scoped draft handling and require communication create permission. Sending does not silently assign an unlinked conversation to a project.
- The calendar defaults to task due dates. A contextual selector also exposes start and follow-up dates. Entries derive from current tasks, so moving, clearing or deleting a task deadline changes the calendar without maintaining duplicate event records. Existing workspace subscriptions and five-second polling synchronize saved changes between users; dirty local edits remain protected. Google event creation remains an explicit action. Invalid dates are excluded, and project calendar duplicate detection uses Jerusalem dates.
- Project profession navigation now reads `תחומי עבודה בפרויקט`; the manager reads `בחירת תחומי עבודה לפרויקט`, with contextual examples inside the new-name field and explicit project-association checkboxes. The email field names its classification purpose directly. Long explanatory paragraphs were removed.
- All Projects has a dedicated customer-name substring search alongside the existing exact customer filter and general search. It supports multiple customers per project, combines with other filters and clears with the reset action.

## Deployment arrangement

`main` is the production source. `staging` is synchronized to the same release commit without force pushing. CI runs for both branches.

`npm run deploy:staging` builds preview mode and uploads a Cloudflare Worker version under the `staging` preview alias. It does not move production traffic. The existing preview notice explicitly states that this version shares the current backend and Google services; this is a code staging environment, not an isolated data sandbox. Fixture browser QA uses separate disposable local data and blocks remote requests.

Production uses the existing Worker, RAM profile, CONFIG binding, schedule and `--keep-vars`. No database migration or business-data rewrite is required.
